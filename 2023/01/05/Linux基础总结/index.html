2.2. 日志管理

2.2.1. journalctl

systemd 自带了一个集中式日志守护进程 systemd-journald，把内核消息、系统服务、你自定义的服务输出，全部收集到一个二进制数据库（存在 /run/log/journal/ 或 /var/log/journal/ 里）。而 journalctl 就是用来查询这个数据库的工具，支持按时间、服务、进程 ID、优先级过滤，甚至实时跟踪。
面试时一句说清：“journalctl 是 systemd 生态的日志查询命令，对应后台的 systemd-journald 服务。它集中管理所有 systemd 单元和内核的日志，支持结构化过滤和持久化存储。”

journalctl持久化：
CentOS 7 最小化安装，journald 的日志默认存在内存里（/run/log/journal），一重启全清空！所以你重启服务器后 journalctl -b -1 查不到上次的日志，不是命令错了，是根本没持久化。

生产级防护：日志轮转 logrotate（防爆盘的根本）

2.5. 进程管理

当我们运行一个程序，那么我们将运行的程序叫进程：

  • 当程序运行为进程后，系统会为该进程分配内存，以及进程运行的身份和权限
  • 在进程运行的过程中，服务器上会有各种状态来表示当前进程的指标信息
    程序和进程的区别：
  • 程序是数据和指令的集合，是一个静态的概念，比如/bin/ls /bin/cp 等二进制文件，同时程序可以长期存在系统中。
  • 进程是程序运行的过程，是一个动态的概念，进程是存在生命周期概念的，也就是说进程随着程序的终止而销毁，不会永久存在系统中

思路：

  1. 谁在吃 CPU？ → top / ps
  2. 谁在吃内存？ → top / ps / free
  3. 谁在等 IO？ → top（看D状态）/ iostat
  4. 谁在占端口/文件？→ lsof / ss

进程状态：
R Running 正在跑，或者在排队等CPU
S Sleeping 在等事件（比如等网络请求回来），正常状态
D Disk sleep 在等磁盘IO，不可中断，kill不掉
Z Zombie 僵尸进程，已经死了但爹没来收尸
T Stopped 被暂停了（比如 Ctrl+Z）
比如说：

  • 生产中看到大量 D 状态 → 磁盘有问题（NFS挂了、磁盘故障）
  • 生产中看到大量 Z 状态 → 父进程有bug，没有 wait() 子进程

5.3.2. 使用LVM管理硬盘

直接分区 + 格式化虽然简单，但如果以后磁盘空间不够，再扩容就很麻烦（只能换更大盘，数据迁移）。LVM 允许你在不停止服务的情况下动态扩容。
层级 L VM 术语 大白话解释 对应你之前的操作
第1层 PV (物理卷) 就是你手上的乐高砖块（物理硬盘 /dev/sdb） 就是你的 /dev/sdb 整块盘
第2层 VG (卷组) 你的大收纳箱，把一堆砖块扔进去合并容量 相当于把100G + 200G 合并成300G的池子
第3层 LV (逻辑卷) 你从收纳箱里切出来的一块具体积木（最终使用的设备） 相当于你之前的 /dev/sdb1，但它是弹性的

6.3.7. 交互脚本expect

expect 不是 Shell 本身的命令，而是个专门干“自动交互”的独立程序。凡是需要你手动敲密码、确认 yes/no 等键盘输入的对话场景，它都能模拟人工去敲键盘。
运维用它最多的就是自动化 SSH 登录、批量传文件、批量改密码这些不能用管道传密码的顽固场景。

ssh、scp、passwd 这些命令为了安全，故意不从标准输入读密码，而是直接读键盘设备（终端）。所以你用 echo “123456” | ssh root@host 登录，密码根本不会被 ssh 接收。expect 就是在中间扮演“假键盘”，把预设好的字符串发给目标命令，让对方以为是人手打的。

expect 脚本的核心就三句话：

  • spawn：启动要交互的程序（比如 ssh）
  • expect：等待屏幕上出现某个特征字符串（比如 password:）
  • send：看到特定字符串后，把要输入的内容发过去（比如密码）

脚本开头：expect脚本一般以#!/usr/bin/expect 开头，类似bash脚本。expect脚本常常以.exp或者.ex结束。
expect主要命令：

  • spawn 新建一个进程，这个进程的交互由expect控制
  • expect 等待接受进程返回的字符串，直到超时时间，根据规则决定下一步操作
  • send 发送字符串给expect控制的进程
  • set 设定变量为某个值
  • exp_continue 重新执行expect命令分支
  • [lindex $argv 0] 获取expect脚本的第1个参数
  • [lindex $argv 1] 获取expect脚本的第2个参数
  • set timeout -1 设置超时方式为永远等待
  • set timeout 30 设置超时时间为30秒
  • interact 将脚本的控制权交给用户，用户可继续输入命令
  • expect eof 等待spawn进程结束后退出信号eof

老手答法：SMTP 是发件协议，端口 25/465，负责邮件传输；POP3 和 IMAP 都是收件协议，POP3 下载后服务器默认删除，适合单设备；IMAP 邮件存服务器，多设备同步，是当前主流。

一封邮件的完整旅程：
发件人（test1）→ MUA 写邮件 → 本地 MTA（Postfix） → 查对方域名的 MX 记录 → 送到收件人 MTA → 收件人 MTA 交给 MDA 存到邮箱 → 收件人（test2）用 MUA 通过 IMAP/POP3 取邮件。

6.5.3. 邮件发送报警设置

mailx 只是个 “写信递信的工具”，它自己不负责长途送信，而是把邮件交给正规的 SMTP 邮件服务器（比如企业邮箱、163/QQ 邮箱）去发。

6.5.4. 补充：解决报错

能发送，但是报错：
Error in certificate: Peer’s certificate issuer is not recognized.
mailx 底层靠 NSS 库做 SSL 证书校验，你只写了ssl-verify=ignore但没指定 NSS 证书目录，校验规则没生效，还是会拦截证书不信任的连接。

方案一：直接给 mailx 指定一个初始化过的 NSS 证书目录，配合忽略校验，彻底跳过证书验证，发告警完全够用。

方案二：正规解法（导入证书，生产更规范）
把 163 邮箱的 SSL 证书导入系统信任库，从根源消除报错，没有任何警告。适合对合规、干净日志有要求的场景。
